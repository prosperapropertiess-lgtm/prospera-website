# 24 — Exception Playbook

## PURPOSE
Give a specific, pre-thought answer for every unusual situation, so the leasing engine never has to improvise from scratch mid-crisis. Serves: all 5 pillars.

## WHEN THIS SOP STARTS
Any time a situation falls outside the normal-path SOPs (01–20).

## RESPONSIBLE PERSON
Leasing Lead; escalate to Ebin where noted.

---

Each exception below: **situation → action → which normal SOP it returns to.**

- [ ] **No direct comparables.** → Run the No-Direct-Comps Pricing SOP (`04_RENT_PRICING.md`). Returns to normal pricing flow with confidence level set to LOW.

- [ ] **Luxury/unique property.** → Same as above, plus widen substitute-property search further; consider whether this property should be scored more conservatively on `01_PROPERTY_ACCEPTANCE.md`'s "market demand" factor given a smaller buyer pool.

- [ ] **Very weak neighbourhood.** → Score honestly on leaseability (`01_PROPERTY_ACCEPTANCE.md`); if accepted, set owner expectations explicitly on likely longer timeline (`03_OWNER_EXPECTATIONS.md`) rather than promising normal velocity.

- [ ] **Poor property condition.** → BLOCKER items must be resolved before launch, no exceptions (`06_RENT_READY.md`). If owner won't address them, this becomes a Property Decline or Conditional Acceptance scenario, revisit `01_PROPERTY_ACCEPTANCE.md`.

- [ ] **Owner refuses price reduction despite funnel data.** → Present the vacancy cost math one time, clearly (Price Reduction Conversation Script, `25_SCRIPT_LIBRARY.md`). If the owner still declines, log it via the Owner Declined Recommendation script and continue at current price — do not re-litigate this repeatedly or pressure the owner. Revisit at the next scheduled checkpoint, not sooner.

- [ ] **Owner wants unrealistic rent from the start.** → State the estimated market range clearly at `04_RENT_PRICING.md`, let the owner make an informed choice. If they insist above range, this is their **[OWNER DECISION]** to make — document it, proceed, and don't let a Day 30 review become "we told you so" — stay in NUMBERS → FEEDBACK → ACTIONS → ASSESSMENT → RECOMMENDATION mode.

- [ ] **Extremely high inquiry volume.** → Good problem — make sure `09_LEAD_MANAGEMENT.md` response-time targets still hold; if volume threatens the 2-hour target, batch showings into fewer, tighter windows rather than letting response time slip.

- [ ] **Zero inquiry volume.** → Immediate LOW VIEWS diagnosis, don't wait for Day 3 checkpoint (`14_FUNNEL_DIAGNOSTICS.md`, `15_VACANCY_ESCALATION.md`). Check channel coverage first — a listing that silently failed to publish somewhere is the most common cause.

- [ ] **Many showings but no applications.** → SHOWINGS + LOW APPLICATIONS diagnosis (`14_FUNNEL_DIAGNOSTICS.md`) — pull objection-reason data, address the specific dominant reason, not a generic re-pitch.

- [ ] **Only unqualified applicants.** → Targeting/qualification problem — review whether listing copy's stated criteria (budget, move date, features) actually match the property; a mismatch attracts the wrong applicant pool.

- [ ] **Repeated no-shows.** → After 2 consecutive no-shows on one listing, review booking-flow friction and confirmation/reminder delivery before assuming it's applicant behavior.

- [ ] **Applicant fraud concerns.** → Follow Red Flag Escalation Procedure exactly (`12_SCREENING.md`) — pause, document neutrally, escalate to Ebin, do not proceed to owner presentation until resolved.

- [ ] **Owner becomes upset.** → Do not get defensive. Acknowledge the specific concern, pull the actual record (communication log, funnel data) rather than arguing from memory, and if Prospera genuinely erred, use the OWN IT → CORRECT IT → EXPLAIN NEXT ACTION → PREVENT RECURRENCE pattern (`16_OWNER_COMMUNICATION.md`).

- [ ] **Owner asks "why isn't it rented?"** → This should never be a surprise question if `16_OWNER_COMMUNICATION.md`'s calendar has been followed — answer directly with current funnel numbers and the specific diagnosis/action in progress.

- [ ] **Property reaches 30+ days vacant.** → Day 30 Full Reset (`15_VACANCY_ESCALATION.md`) is mandatory, not optional, at this point.

- [ ] **Prospera made an incorrect rent estimate.** → Acknowledge directly, re-run pricing with updated market data, apply OWN IT → CORRECT IT pattern in the next owner update.

## COMMON MISTAKES
- Treating an exception as a reason to abandon the base SOPs entirely instead of returning to them once the exception is handled.
- Improvising a new approach for a situation already covered here instead of checking this file first.

## ESCALATION CONDITIONS
- A situation arises that isn't covered by any row above → handle it as best judgment allows, then add it to this file afterward so it's covered next time. The playbook should grow, not stay static.

## QUALITY CONTROL
- This file is reviewed and expanded after any real situation it didn't already cover.

## OUTPUT / DELIVERABLE
A pre-thought answer for every listed unusual situation, each one returning cleanly to the relevant normal-path SOP.
